## Frozen E0-E purpose to preserve

E0-E is the mandatory **single-model playwright control**. It uses the same frontier model as the E0-A reference configuration, with matched supported generation/reasoning settings where applicable. That one model receives the complete relevant Scene setup and portrays all three Characters as a playwright.

The comparison exists to isolate Ensemble's separately contextualized-performer architecture from provider/model choice. If the control differs from E0-A on another feasible variable without an explicit experimental reason, the comparison is confounded and the preparation fails.

## Ownership and authority

The evidence lane owns this control arm by Director decision. Engineering may supply bounded implementation help, but E0-E does not gain authority over Core, the E0-A Harness, product surfaces, ODR decisions, provider admission, phase changes, or Blueprint amendments.

E0-E remains throwaway experimental control code/evidence. Its result is an input to the Director, not a self-executing product decision.

## Preparation objective

Produce a control arm that is sufficiently specified—and, only if that specification passes recursive audit, sufficiently preconstructed without network execution—that once E0-D is closed the project can activate E0-E without inventing behavioral rules after seeing E0-A-D results.

Preparation should minimize future degrees of freedom while avoiding premature fixation of volatile provider facts that must be inherited from the eventual exact E0-A reference configuration.

## Falsification-first criterion

Reject the preparation if any of the following is true:

- it uses a different underlying model/provider identity from the E0-A reference configuration without a separately labeled reason;
- supported generation/reasoning settings are not matched where feasible;
- it changes the frozen fixture/Character/world condition rather than only the architecture under comparison;
- it quietly gives Ensemble or the playwright arm extra information, extra retries, a different evaluation rubric, or a different acceptance standard;
- it cannot preserve technical failure separately from experiential quality;
- the scoring package can identify the arm before scoring is recorded;
- implementation leaks into Core/product runtime or becomes a second production architecture;
- preparation itself consumes provider traffic, credentials, spend, E0-E run budget, or evaluation results.

## Preparation deliverables

The fresh chat should recursively audit and freeze the smallest adequate packet covering:

1. **Control identity and hypothesis** — exact statement of what architectural variable E0-E removes and what result would challenge Ensemble's complexity.
2. **Reference-configuration binding** — how the control inherits the eventual exact E0-A provider/model/settings identity without copying stale values from today's provider experiments.
3. **Complete Scene input contract** — what constitutes the complete relevant Scene setup for the playwright, including world truth, Character definitions/state, relationships, pressures, Scene state, and prior accepted causal history relevant to the run.
4. **No isolated-cast machinery** — explicitly identify which Ensemble mechanisms are absent so only the intended architectural variable changes.
5. **Playwright output contract** — one model portrays all three Characters in a form that can be converted into the same blind-review unit as E0-A without granting the control extra expressive channels.
6. **Turn/scene progression rule** — deterministic limits and stopping behavior sufficient to make run length/opportunity comparable without recreating Ensemble's isolated Performer routing inside the control.
7. **Failure and integrity boundary** — technical refusal/error/cancellation/malformed output must remain non-fiction and separately attributable; E0-E need not use the exact E0-A Candidate API but remains subject to auditable hard integrity gates.
8. **Retry, cancellation, and spend envelope** — matched/fair deterministic rules for the later live run, while leaving actual provider authorization and current pricing/quota verification to the execution gate.
9. **Provenance** — Run ID, Blueprint/fixture identity, exact reference configuration identity, request/settings identity, timestamps, outcomes, and evidence sufficient for later audit.
10. **Blind evaluation compatibility** — neutral labels, frozen rubric before transcripts exist, equivalent transcript normalization, scorer independence, and unblinding only after scores are recorded.
11. **Throwaway implementation boundary** — location/dependency rules that keep control scaffolding outside Core and out of product architecture; deletion after E0 must remain cheap.
12. **Activation checklist** — exact conditions that must be true after E0-D before E0-E execution can begin.
