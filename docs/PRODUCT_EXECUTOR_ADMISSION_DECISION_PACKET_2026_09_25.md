## Product semantics versus execution infrastructure

Product continues to own the explicit `SceneId + CharacterId` Opportunity; established Scene/Cast/initial-roster checks; context consisting only of SceneId, CharacterId, CharacterName and the actor's committed Circumstances across Scenes; candidate validity; exactly one additive actor Circumstance; provisional acceptance; atomic persistence and causal revision freshness.

The executor edge owns request encoding, role instructions, response parsing/validation, technical correlation, transport/resource lifetime and technical failure evidence. It receives only the Product context and, for the interpreter, the exact candidate from this invocation. Production ID, UI witnesses and technical request metadata can remain with the owner; they do not silently become actor context. No catalog, filesystem, Application object, full replay, other actor state, World truths or prior transcript is exposed to the executor. Provider responses are untrusted proposals, never persistence commands.

Use separate Performer and interpreter invocations even if they share a stateless transport. The Performer returns only visible text; the interpreter proposes the single Circumstance from the same context plus that exact candidate. Do not reuse provider conversation state, retrieve hidden context, add an Integrity role, select another actor, invent a default Circumstance, manufacture silence on provider failure or retry another model until something passes. Unsupported/partial/malformed/refused output is a technical executor failure unless valid Product output was actually received. Genuine empty Performance text remains valid; whitespace-only/invisible/malformed nonempty Performance text is rejected by existing Product validation. No silent trim/normalization/repair or changed Circumstance validator is proposed.

## Serialized invocation and result publication contract (proposed)

1. **One owner per Application instance.** A bounded coordinator controls every access to that instance, including Query and navigation, not only Perform. The existing UI may use it synchronously while idle; it transfers exclusive access to one worker for the whole synchronous Perform call. A second Application instance over the same Production is not a substitute for ownership. UI bindings read the last published immutable projection while pending.
2. **Capture before dispatch.** Validate admission, current open Production and resolved Scene/Character witnesses while owning Application access. Capture a session-only request token, Application/session generation, open-Production generation, ProductionId, SceneId, CharacterId, expected history revision, and exact display/focus witnesses. Name/code/index/focus alone never identifies the target. Recheck the captured Production, target and revision under ownership immediately before calling Perform; reject a stale unstarted request without executor calls.
3. **Acquire before notifying or awaiting.** Transition atomically from ready to pending before property notifications, callbacks or the first await. Exactly one accepted activation calls Perform once. Reject duplicates/reentrant commands rather than queueing them for later execution. Disable and guard all Product commands and all in-app navigation, including Back/Home/Productions/Settings/ProductSpace/contextual paths. Disabled controls alone are insufficient; programmatic and keyboard entry points must share the guard. An executor cannot reenter Application.
4. **Keep the dispatcher responsive.** Publish `Requesting Performance…` and pending focus on the UI dispatcher, then run the synchronous operation off that dispatcher under the exclusive lease. `Task.Run` is a possible scheduling mechanism only after ownership, gate and publication guarantees exist. No UI `.Wait()`/`.Result`, worker UI writes, lock held across a dispatcher wait, or callback that requires UI progress to finish. A synchronous bridge to an async transport must be off-UI and proven not to capture/wait on that dispatcher. If the selected runtime cannot satisfy this, return for a bounded async/runtime disposition rather than changing Product casually.
5. **Retain ownership to classification.** No competing Query/Open/Recover/mutation can run while Perform is outstanding. Do not release the lease merely because the view unloads, a timer fires, an await is abandoned or a token is cancelled. No cancellation/timeout/rollback guarantee is created. Runtime timeout faults, if later admitted, end work only when the worker actually terminates; they do not establish Product noncommit. OS termination is an interruption, not cancellation.
6. **Capture the terminal result before rendering.** On worker completion, store an immutable session record containing the captured request identity, terminal category, known outcome and exact successful `PerformanceExecution` (or technical diagnostics without guessed content). The successful returned object is this request's attribution evidence. Do not query “latest,” compare text/counts or infer identity from replay membership. Capture any fresh Application projection under ownership; finish state transfer before publishing it to UI.
7. **Publish once to the matching target.** Dispatch a completion tied to the request token and generations. Only the matching pending operation may replace its view, release its command gate or announce completion. Duplicate/late callbacks cannot release another request's gate. A mismatching result must not paint a different Production/Character or be treated as permission to retry. Retain any known success against its original request; freeze affected request activity and classify the ownership fault conservatively. Stale UI rejection does not undo a committed event. External durable history races are handled independently by the existing locked pre-append revision check; never silently rerun after rejection.
8. **Maintain uncertainty across navigation.** Track the block by ProductionId for the session. Leaving/returning, switching to another Production or failed Open does not clear it. Only successful ordinary Open of that same Production clears its stale-state block; Recover is not an invented substitute. Keep the earlier unconfirmed outcome and warning that another request may record another Performance. Open cannot attribute or repair the earlier request. Tokens/generations are not persisted and supply no cross-restart deduplication or exactly-once guarantee.

The owner is an application-host coordination boundary, not a new Product scheduler, persistent request journal or generalized orchestration service. Holding a coarse exclusive lease across this one slow operation is deliberate because the adopted UI already blocks all other operations while it is pending.

## Failure, uncertainty and post-commit presentation

Record **technical cause** and **Product commit knowledge** separately. A provider timeout may leave provider usage/spend unknown while Product noncommit is provable because the exception escaped before commit. Conversely, a persistence failure may leave Product outcome unknown without being a provider failure. Current `ProductAccessResult<T>` exposes only Success / Invalid / Incompatible; it cannot support invented fine-grained commit assurances.

| Classification | Evidence and behavior |
|---|---|
| Known noncommit | Admission or target refusal before dispatch; or a positively attributed executor exception escaping from Perform/Interpret before Product reaches its committer, with no independent persistence capability or reentrancy. Record noncommit only from that bounded control-flow evidence. No automatic retry; no claim that no provider request/spend occurred. This is an internal classification, not permission to invent new creator copy. |
| Outcome unknown | Any typed `Invalid` returned from Perform, invocation I/O/access failure, interrupted/lost completion, or unexpected fault without proven commit position. Invalid can occur after committer success (`ProductApplication.cs:346-367`); exception class alone does not locate a fault. Preserve target witness, block this Production for the session, require successful ordinary reopen, and never say “nothing was saved.” |
| Product incompatibility | Preserve typed `Incompatible` and the adopted **Performance unavailable in this version.** message. Restore Back; no automatic retry/migration/upgrade action. Provider protocol/model unsupported is not Product persistence incompatibility. Do not infer a generic commit-status contract from the enum. |
| Executor/provider/runtime failure | Missing capability, authentication/authorization failure, transport/service failure, quota/resource exhaustion, malformed/unsupported output or runtime fault remains a technical category. Missing admission means **Performance is unavailable.** and disabled Request. Never recast technical failure as Character refusal, silence, Product corruption or Product Invalid. Commitment knowledge follows the evidence rules above. |
| Known success with presentation failure | A successful returned Application result establishes a recorded outcome before formatting, binding, focus or rendering. Retain it even if those later steps fail; report the display problem while preserving **Performance recorded.** No failed-request/retry affordance, re-execution or rollback implication. |

The adopted conservative UI remains binding: typed Invalid uses **Performance not confirmed. Kymaean could not confirm whether this Performance was recorded.** Invocation I/O/access failure uses **Confirmation unavailable. Kymaean could not confirm whether this Performance was recorded.** Even if a later adapter can internally prove a narrower precommit failure, this packet does not amend that copy or weaken its block. Any desired less-conservative creator branch returns for Design/Product disposition.

Success presents exact returned accepted text and exact `AcceptedPerformance.Consequence.Text` as one result. Empty text uses **No visible Performance text.** outside the content field. Keep content fully reachable and separate from diagnostics; do not publish raw provider output, partial streaming content or an uncommitted candidate. A failed render may recover the view from its retained session record; that is display recovery, not a new request/history query. Leaving closes the transient view with the adopted permanence warning. Completion/focus announcements are once per request and do not automatically narrate long content. No Take/review/undo/continue action is introduced.
