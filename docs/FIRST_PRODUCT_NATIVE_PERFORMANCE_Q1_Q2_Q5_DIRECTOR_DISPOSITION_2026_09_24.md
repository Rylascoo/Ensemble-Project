## Q1 — E0 -> Product acquisition mode

**ADOPTED FOR THIS MILESTONE: Product-native semantic port.**

- `Kymaean.Application` remains independent of `Ensemble.E0.Core`.
- E0 is evidence/oracle input, not Product type authority.
- Product owns its own Opportunity, bounded Character context, Performance candidate, consequence-interpreter seam, provisional acceptance policy, causal Product event and Product history revision.
- No E0 `ProductionState`, `StateHash`, `RecordId`, `ContextPacketId`, fixed-three roster law, provider/run identity or full E0 ontology crosses into Product.
- Product Performance text may re-derive validated Character-legible semantic invariants without taking an E0 runtime dependency.

Falsifier preserved: if this vertical cannot remain Product-owned without materially duplicating a mechanism that demonstrably requires one shared generalized implementation across E0 and Product, extraction/generalization must be reconsidered.

## Q2 — minimum Character context/access

**ADOPTED FOR THIS MILESTONE: explicit actor-bound context.**

An Opportunity is an explicit existing `SceneId + CharacterId`.

Before Performer invocation:

1. the Scene must already be established;
2. the Character must exist in the Production Cast;
3. the Character must belong to that Scene's initial roster.

The bounded acting-Character context contains exactly:

- SceneId;
- CharacterId;
- CharacterName;
- that Character's own committed Character Circumstances.

It does not contain World-current truth, another Character's Circumstances, Knowledge, Belief, Memory, Goal, Relationship, Pressure, Observation, UnresolvedProposition, recent Performance text, provider state, automatic opportunity selection or Current/Active Scene semantics.

The access shape is **Product re-derivation informed by E0 evidence**, not adoption of E0 Access/Context types.

Falsifier preserved: if a valid first-Performance case cannot authorize from established Scene + initial roster + Character identity, or cannot deliver the committed consequence to the same actor later without broader authority, this bounded context is insufficient.

## Q5 — first consequence domain

**ADOPTED FOR THIS MILESTONE: exactly one additive Character Circumstance per accepted first-slice Performance.**

- Character Circumstance is deliberately the first narrow durable consequence family.
- The Performer proposes only visible Performance.
- A separate invocation-scoped consequence interpreter proposes the Circumstance.
- The provisional deterministic first-slice acceptance policy accepts that bounded package.
- One Product event atomically records accepted visible Performance plus exactly one Character Circumstance consequence.
- Rejected/failed/uncommitted candidate work does not enter Product history.
- Zero-consequence accepted Performance, broader consequence families and final Take/consequence-review semantics remain outside this first milestone; ODR-19 stays open.

Falsifier preserved: if a semantically coherent first accepted milestone case necessarily requires non-additive replacement/deactivation, global/Scene truth, epistemic state, Disposition or Relationship rather than one immediate actor Circumstance, this first consequence family must be revised under new authority.

## Exact-history freshness refinement

Independent review demonstrated that semantic replay equality alone is insufficient because an idempotent or ABA journal advance can change causal history while restoring the same visible projection.

The Product-native implementation therefore uses an opaque Product `ProductionHistoryRevision` derived from authoritative durable event count. It is not E0 `StateHash`. Performance commit compares the complete expected Product replay, including this revision, against authoritative source history **inside the journal lock before append**.

This is an implementation correctness refinement inside the adopted Q1 seam, not an expansion into E0 ontology.
