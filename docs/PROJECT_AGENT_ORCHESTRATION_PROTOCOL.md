# Ensemble Project Agent Orchestration Protocol

Status: ACTIVE CROSS-PROJECT WORKFLOW LAW

Version: 1.0

Date: 2026-09-09

## 1. Purpose

This document defines how the Director, Engineering Sol, Design Sol, the future Ensemble Project Administrator, Codex execution agents, scarce specialist models, and independent reviewers cooperate without duplicating authority or making chat history the project memory.

It changes collaboration and execution routing only. It does not alter the frozen Ensemble Blueprint, E0 experiment order, product constitution, provider authorization, repository residency, validation hierarchy, design law, or any active `CURRENT_STATE.md` boundary.

The durable operating principle is:

> **Parallelize mechanics, not authority.**

Multiple agents may inspect, implement, test, browser-preflight, or independently falsify work in isolated contexts. Authoritative interpretation and project-state changes remain owned by the Director and the accountable lane manager under repository law.

## 2. Authority hierarchy

For any routed task, resolve authority in this order:

1. frozen product/phase law and explicit Director decisions;
2. the owning repository's current authority and exact `CURRENT_STATE.md` boundary;
3. the accountable lane manager's in-lane judgment under delegated authority;
4. executor/reviewer/tool evidence.

External execution never promotes itself into authority.

A dispatch packet transports work. A PR transports a candidate change. A test transports evidence. None of them creates authority by existence.

## 3. Roles

### Director

The Director owns:

- product constitution;
- ODR resolution;
- provider admissibility and spend authorization;
- consequential architecture/scope changes;
- final subjective product/visual taste where evidence cannot decide;
- native/external execution gates that require the Director's machine/account/approval.

The Director should not be used as a manual router for facts or prompts that repository authority or an accountable Sol can construct.

### Engineering Sol

Engineering Sol is the accountable engineering manager for `Rylascoo/Ensemble-Project`.

It owns engineering reasoning, architecture interpretation, patch boundaries, source/test/evidence reconciliation, validation interpretation, Engineering queue transitions, recursive audit, and final engineering adoption under current authority.

Engineering Sol may delegate bounded execution but must reconcile returned evidence before project state changes.

### Design Sol

Design Sol is the accountable design/brand/app-visual/website manager for `Rylascoo/Ensemble-Website` and the canonical visual-master workspace in Drive.

It owns design interpretation, method fidelity, visual judgment, design evidence, and in-lane adoption. Engineering facts are truth inputs; Engineering does not become aesthetic authority.

### Ensemble Project Administrator

The future Administrator is an **operational dispatcher and project-operations agent**, not a third project authority.

It may:

- resolve exact refs, queue state, CI, branch/worktree status, and known external-dependency state;
- identify prerequisites, blocked work, and cross-lane consultation needs;
- construct bounded work packages;
- create isolated Codex worktrees/execution contexts;
- dispatch mechanical implementation, repository, browser, test, and audit work;
- collect returned evidence;
- prepare Director/Claude/manual relay packets when a surface cannot be invoked automatically;
- flag continuity drift and administrative cleanup debt.

It may not:

- redesign frozen architecture or design methods;
- resolve an ODR;
- authorize provider traffic/spend;
- promote validation;
- choose final design taste;
- silently adjudicate Engineering-vs-Design disagreement;
- mutate an owning lane's authority merely because a mechanical task completed.

The Administrator must remain replaceable. GitHub repositories, not its chat/session memory, are project memory.

### Codex execution agents

Codex is an execution environment/agent surface. It is not synonymous with any particular model.

A Codex worker may be used for bounded work that benefits from local checkout/worktree access, repository-scale mechanics, tests, scripts, browser/CDP, computer use, or implementation tooling.

Codex workers must start from an exact work-package contract and return evidence. They do not silently reinterpret task scope.

### Scarce specialist model

A high-capability/limited-allowance model such as GPT-6 Astra may be used inside Codex when capability advantage materially changes expected reliability or information gain.

Scarcity is an allocation property, not project authority.

Use such a specialist for hard codebase-scale audits, difficult browser/runtime/computer-use diagnosis, complex cross-cutting transformations, or deliberate high-capability independent falsification. Do not spend it merely because a task is tedious or large.

### Independent reviewer

A separate model/context such as Claude Chat or Claude Code may be used when genuine independence adds information: adversarial falsification, alternate diagnosis, architecture/security/regression review, or consequential design-method critique.

Independent review is evidence, not authority. It is not required ritual for every patch.

Until the dedicated Claude operating protocol is established, do not assume automated Claude connectivity, a billing mode, or a fixed model recommendation.

## 4. Repository authority and message transport

Canonical project memory remains:

- `Rylascoo/Ensemble-Project` for engineering, product/policy, central queue, cross-project orchestration law;
- `Rylascoo/Ensemble-Website` for design/brand/UI/website law and evidence;
- connected Google Drive `Ensemble Project` for visual-master/provenance assets.

`docs/PROJECT_EXECUTION_QUEUE.md` remains the **single cross-project backlog/sequencing register**. No Administrator inbox, GitHub Issue set, Codex task list, Claude thread, or chat creates a second backlog.

A future GitHub-based dispatch surface may carry cross-lane questions/results. Until that transport is explicitly activated during Administrator setup, agents must not pretend automatic cross-chat routing exists.

If automatic transport is unavailable, the accountable Sol or Administrator produces a complete copy/paste packet for the Director. The Director should not have to author or infer the prompt.

## 5. Dispatch packet contract

Every consequential routed task must identify, as applicable:

```text
SOURCE ROLE:
TARGET ROLE / SURFACE:
QUEUE ITEM:
SOURCE REPOSITORY + EXACT REF:
TARGET REPOSITORY + EXACT REF:
QUESTION / TRANSFORMATION:
AUTHORITY ALREADY GRANTED:
ALLOWED SCOPE:
PROHIBITED SCOPE:
EXPECTED EVIDENCE / RETURN ARTIFACT:
STOP / FAILURE CONDITIONS:
RETURN TARGET:
MODEL / REASONING / MODE / USAGE CLASS:
```

Model/reasoning fields are execution metadata. Verify current tooling capability before dispatch rather than treating a historical model name as law.

A recipient must race-check relevant refs before acting. If the baseline moved materially, stop or reconstruct the packet rather than applying a stale change.

## 6. Work-package contract for executors

A Codex/Astra/Claude Code work package should normally contain:

- one bounded falsifiable objective;
- exact repository/ref baseline;
- exact allowed files/surface or a clearly bounded search domain;
- machine-checkable expected output when practical;
- non-goals and prohibited mutations;
- required validation/test/browser steps;
- failure/stop conditions;
- evidence/provenance to return;
- authority that remains outside the executor.

Do not combine unrelated audits merely to fill an expensive model session.

## 7. Independence / review classes

Use independent review only when its information value warrants the cost.

### R0 — mechanical

Executor self-check + machine validation/CI is sufficient unless a defect appears.

Examples: generated indexes, deterministic reference checks, branch census scripts.

### R1 — ordinary

Executor + owning Sol recursive audit.

Examples: normal bounded patch, ordinary browser materialization from a frozen method.

### R2 — consequential

Owning Sol + one independent reviewer when a separate context materially reduces risk.

Examples: provider-adapter semantic change, important accessibility/browser mechanism, substantial refactor.

### R3 — critical

Owning Sol + independent review + optional scarce specialist falsification.

Examples: causal-history/security architecture, E0 convergence, repository-wide integrity migration, pre-release architecture.

### R4 — Director

Evidence is reconciled first, then the Director decides the product/policy/taste/authorization question.

Review classification cannot lower a validation requirement or provider/security gate.

## 8. Cross-lane consultation

Engineering Sol and Design Sol may refer questions to each other without transferring authority.

Design -> Engineering examples:

- what runtime/product state actually exists;
- whether a proposed interaction can truthfully correspond to current architecture;
- whether a motion/disclosure requirement conflicts with deterministic/privacy constraints;
- whether a public product claim is implemented/validated.

Engineering -> Design examples:

- what visual/interaction requirement a product state must preserve;
- what accessibility or identity carrier a UI implementation must support;
- whether a technical fallback remains semantically/visually truthful;
- whether an implementation candidate violates frozen design law.

If lanes disagree, each manager states its authoritative facts/inferences. The Administrator does not split the difference. Escalate only the genuinely unresolved authority question.

## 9. Single-writer / integration discipline

Parallel work is encouraged for independent mechanics, but authority surfaces need clear ownership.

- `CURRENT_STATE.md` is written only as part of the owning lane's reconciled closure.
- the central execution queue is reconciled as one logical closeout operation, not independently edited by competing agents;
- Design Ledger writes remain Design-owned;
- provider authorization/validation records remain governed by Engineering/Director authority;
- external reviewers normally return findings rather than editing authority files directly.

When concurrent work exists, use isolated branches/worktrees and rebase/reconstruct on the latest authoritative tip before promotion.

## 10. Validation and evidence

Agent confidence never substitutes for validation.

Engineering validation remains:

`static reasoning < compiler < target-device runtime < hardware/NPU evidence < package/WACK < Store/Partner Center certification`.

Browser/CDP evidence establishes browser behavior only. It does not establish WinUI/native Windows accessibility/runtime claims.

An independent model review is not machine validation.

A provider-bound call is an external execution/spend event and requires the applicable Director/provider authority regardless of which agent can technically invoke it.

## 11. Model and effort recommendations

Exact model menus, effort controls, plan limits, and billing behavior are volatile. `docs/AGENT_TOOLING_CAPABILITY_SNAPSHOT.md` records the current operational recommendation.

Whenever the Director must invoke an external surface manually, the owning Sol or Administrator must provide:

```text
SURFACE: ...
MODEL: ...
REASONING/EFFORT: ...
MODE: ...
USAGE CLASS: normal | scarce
```

followed by one complete paste-ready prompt.

Do not ask the Director to choose a model/effort level from scratch when project management can make the recommendation.

## 12. Fresh-chat and handoff retirement

Long handoffs and personality prompts are transitional evidence, not durable project memory.

A fresh lane chat should be able to begin from a minimal pointer such as:

```text
Resume Engineering Sol from Rylascoo/Ensemble-Project.
```

or:

```text
Resume Design Sol from Rylascoo/Ensemble-Website.
```

The receiving agent then executes the owning repository's `AGENTS.md` bootstrap and exact-ref reconciliation.

Historical handoffs remain useful for provenance only when current authority points to them or a narrow ambiguity requires archaeology.

## 13. Automation rollout rule

Do not automate a process merely because a tool can invoke it.

Roll out in this order:

1. repository law and authority separation;
2. explicit manual work-package/dispatch contracts;
3. Codex Administrator setup;
4. repository-native Skills that execute existing law;
5. bounded browser/engineering pilots;
6. independent-review integration;
7. hooks/automations only after repeated manual behavior proves stable and worth automating.

Skills/hooks execute project law; they do not redefine it.

## 14. Recursive audit and closeout

Any material orchestration/process change must be recursively audited for:

- authority leakage;
- duplicate backlog/state surfaces;
- imaginary automation;
- stale model/tool assumptions;
- cross-lane write hazards;
- validation inflation;
- provider/spend leakage;
- branch/worktree lifecycle;
- whether the Director is being used as avoidable manual middleware.

After a material correction, restart the relevant audit. Stop when one complete pass finds no material error, authority inconsistency, unsupported automation claim, avoidable duplicate authority surface, validation/billing ambiguity, or worthwhile in-scope simplification.
